# Agent project handoff contract

> Decision date: 2026-07-31
>
> Scope: the first public SideRefresh release for Agent app makers

This document defines how Claude Code, Codex, Cursor, and similar coding agents
can bring an Agent-made personal app into SideRefresh without choosing the
user's signing identity, iPhone, renewal schedule, or install action.

It is an implementation contract, not an implementation. The Simple workspace
continues to own setup and user review.

## Decision

A coding agent may hand SideRefresh exactly one local Xcode container path:

- an absolute `.xcodeproj` path; or
- an absolute `.xcworkspace` path.

The handoff is a non-authoritative suggestion. SideRefresh independently
inspects the container, launches or activates the macOS app, and presents the
proposal inside its existing project picker. Nothing is saved, installed, or
scheduled until the user completes the normal in-app review and confirmation
flow.

MCP and CLI are adapters over the same Project handoff interface:

```text
MCP handoff_project ─┐
                     ├─> Project handoff Module ─> SideRefresh project picker
CLI project handoff ─┘                                  │
                                                       ├─> review proposal
Direct file selection ─────────────────────────────────┤
Authorized-folder scan ────────────────────────────────┘
```

Direct selection and scanning of user-authorized folders remain visible
fallback paths. Agent handoff does not replace them or create a second setup
workflow.

## Interface

### MCP

```json
{
  "name": "handoff_project",
  "arguments": {
    "container": "/absolute/path/MyApp.xcworkspace"
  }
}
```

`container` is the only input. The tool does not accept a scheme, target, Team
ID, bundle identifier, product, iPhone, Derived Data path, schedule, install
flag, or confirmation Boolean.

Recommended MCP annotations:

```json
{
  "readOnlyHint": false,
  "destructiveHint": false,
  "idempotentHint": true,
  "openWorldHint": false
}
```

The tool is not read-only because it creates ephemeral pending state and
launches or activates the app. It is non-destructive and idempotent for the
same canonical path.

### CLI

```shell
side-refresh project handoff \
  --container "/absolute/path/MyApp.xcworkspace"
```

The command has the same validation, pending-state behavior, result codes, and
review requirement as MCP. It is not an alias for the existing full
configuration save command.

### Success result

Opening a new review returns:

```json
{
  "status": "review_opened",
  "request_id": "opaque-request-id",
  "container": "/absolute/path/MyApp.xcworkspace",
  "requires_user_review": true,
  "target_changed": false,
  "automation_changed": false,
  "install_started": false
}
```

Repeating the same canonical path while its review is already pending
reactivates SideRefresh and returns `review_already_open` with the same request
identifier.

The result does not return the Team ID, connected-device details, current
configuration, source contents, or renewal logs. A successful result means
only that SideRefresh opened the review surface. It does not report whether the
user later accepted, cancelled, saved, or installed.

### Errors

The interface uses stable machine-readable codes:

| Code | Meaning | Pending state |
| --- | --- | --- |
| `invalid_container_path` | The input is not an absolute `.xcodeproj` or `.xcworkspace` path | Unchanged |
| `unreadable_container` | The exact container is missing, unreadable, or structurally unusable | Unchanged |
| `app_not_found` | SideRefresh is not installed at a supported location | No new pending record |
| `launch_failed` | The app exists but could not be launched or activated | No new pending record |
| `handoff_in_progress` | A different canonical path already has an open review | Existing record unchanged |

An Xcode container with no recognized iOS app target is not rejected merely
because it was generated by a new or unfamiliar tool. It opens as an
`unverified` proposal and the user may complete supported fields manually.

## Inspection boundary

Before review, SideRefresh may inspect only static metadata reachable from the
exact container:

- requested path, canonical path, existence, readability, and container type;
- workspace references needed to identify contained Xcode projects;
- iOS application target candidates;
- scheme, product, bundle identifier, and Team ID candidates;
- an app icon candidate.

The handoff must not:

- scan the user's home folder, parent folder, sibling folders, or recent files;
- read application source contents;
- invoke `xcodebuild`;
- execute build phases, scripts, package plugins, or project-provided tools;
- write the active configuration, Last verified evidence, logs, or schedule;
- automatically choose a target, scheme, Team ID, iPhone, or candidate.

The Module canonicalizes aliases and symbolic links for equality and conflict
checks. If the requested and resolved paths differ, the review surface shows
both before the user accepts the proposal.

The macOS app re-inspects the path when it receives the request. Data observed
by the MCP or CLI process is not trusted as current or authoritative.

## Review behavior

The handoff routes into the existing project picker as a preselected proposal:

1. SideRefresh launches or becomes active.
2. The project picker opens and shows the inspected proposal.
3. The user reviews the exact container and detected candidates.
4. `Review this project` copies the proposal into the Setup draft only.
5. The normal Setup confirmation saves a renewal target.
6. Installation and automation remain separate, explicit actions.

The picker continues to offer direct `.xcodeproj` or `.xcworkspace` selection
and scanning of user-authorized locations. A failed or cancelled handoff must
not make those fallback paths unavailable.

### Existing active target

If SideRefresh already has an active renewal target, the review shows the
current target beside the proposed project.

- Before `Review this project`, the Setup draft is unchanged.
- Accepting the proposal fills only the Setup draft.
- The current target and its automatic renewal remain active until the normal
  save confirmation succeeds.
- Cancelling preserves the current target, schedule, current run, and Last
  verified evidence.

The handoff never interrupts an in-progress renewal.

## Pending-state contract

SideRefresh supports one pending Project handoff:

- the pending record contains only an opaque request ID, canonical container
  path, creation time, and origin (`mcp` or `cli`);
- the same canonical path is idempotent and reopens the existing review;
- a different path returns `handoff_in_progress`;
- accepting or cancelling the review clears the record;
- quitting SideRefresh clears the record;
- no durable handoff history or queue is created.

There is no callback, acceptance token, polling endpoint, or handoff-status
tool. The coding agent yields control to the user after `review_opened` or
`review_already_open`. Existing overall status commands do not gain pending
handoff or user-decision fields.

## MCP safety profiles

The MCP server defaults to a `user-reviewed` profile:

| Default tools | Purpose |
| --- | --- |
| `get_status` | Read current high-level status |
| `handoff_project` | Open a native user review |
| `dry_run` | Run existing non-mutating diagnostics |

The following mutating tools appear and dispatch only when the server is
started with the explicit `--allow-headless-mutations` option:

- `configure_target`;
- `renew_now`;
- `enable_schedule`;
- `disable_schedule`.

Without the option, the server excludes those tools from its advertised tool
list and rejects direct calls as unavailable. A tool argument such as
`confirm: true` cannot elevate the default profile.

The CLI's existing advanced commands remain available. This profile boundary
changes the default Agent app maker integration, not the supported headless
operator workflow.

## Module and adapters

Implement one concrete Project handoff Module shared by the MCP and CLI
adapters. Its Interface owns:

- path validation and canonicalization;
- bounded static inspection;
- single-pending-request arbitration;
- app discovery, launch, and activation;
- stable results and error codes.

The SideRefresh app is the consuming adapter. It converts the pending path into
the existing project-picker proposal and Setup draft. The Xcode container
scanner remains the metadata Implementation behind the Module; the handoff
must use exact-container inspection rather than broad discovery.

The observable Interface stays independent of the local transport used to
cross into the app. A temporary file, local IPC service, or another private
transport may be selected during implementation without changing callers.

Do not add a custom URL scheme in the first release. URLs would expose local
paths to more logging and registration surfaces while adding another public
adapter without a demonstrated need.

Do not introduce a protocol for the Project handoff Module until a second real
Implementation exists. The result and error values are already the testable
Interface.

## Acceptance matrix

| Scenario | Required observable result |
| --- | --- |
| Valid absolute project path, no active target | Picker opens with proposal; configuration, automation, and install remain unchanged |
| Valid workspace path, active target exists | Current and proposed targets are shown; active renewal continues |
| Same canonical path submitted twice | Existing review reactivates; one request ID and one pending record remain |
| Different path submitted during review | `handoff_in_progress`; first review is unchanged |
| Relative path or wrong extension | `invalid_container_path`; app state is unchanged |
| Missing or unreadable container | `unreadable_container`; app state is unchanged |
| Unrecognized generated project | Review opens as unverified; no candidate is selected automatically |
| Requested path resolves through an alias or symbolic link | Requested and canonical paths are visible; canonical path controls idempotency |
| SideRefresh is absent | `app_not_found`; no pending record remains |
| User cancels review | Active target, draft, schedule, evidence, and current run are unchanged |
| User accepts proposal | Setup draft changes; active target does not |
| User saves Setup | Existing validation and confirmation path decides whether the active target changes |
| User selects a file directly | Existing picker flow works without MCP or CLI |
| User scans an authorized folder | Existing discovery flow works without MCP or CLI |
| Default MCP starts | Only `get_status`, `handoff_project`, and `dry_run` are listed and callable |
| MCP starts with mutation opt-in | Four existing mutating tools are additionally listed and callable |
| App quits with review pending | Pending record is cleared; no configuration or history is created |

Tool-list tests and call-dispatch tests both enforce the MCP profile boundary.
Module tests enforce path canonicalization, inspection limits, idempotency,
conflict behavior, and cleanup. App acceptance tests enforce the separation
between proposal, draft, saved target, install, and automation.

## Explicit non-goals

The first release does not provide:

- automatic discovery of whatever project an agent recently created;
- source-tree or home-directory monitoring;
- multiple pending apps, queues, or batch handoff;
- multiple iPhone selection or team equipment management;
- remote project paths or source upload;
- an agent-selected signing identity, device, or renewal schedule;
- headless install as part of `handoff_project`;
- a decision callback to the coding agent;
- a second Agent-specific setup screen.

The existing full `configure_target` capability remains an advanced,
explicitly enabled headless interface. It is not the default path for Agent app
makers.

## Deletion test

Deleting MCP and CLI handoff adapters later must leave direct project selection,
authorized-folder scanning, the project picker, Setup validation, renewal, and
Last verified evidence intact.

Deleting the Legacy workspace later must leave the Project handoff Interface
and Simple project-picker review intact.

If either deletion requires recreating target selection, saving, installation,
or scheduling rules inside the handoff Module, the seam is too broad and the
implementation fails this contract.
